# The test suite runs faster and never weaker

## 1. ASSESS — Problem Understanding

### What the owner asked

> "can we make the test building agent smarter so that test run faster, websearch best practices" (2026-10-12)

His brief to the CTO Chief, in substance: the suite runs faster and never weaker. Every test keeps or tightens what it proves; a moved test keeps its assertions word for word. Slices, in his order: (1) split `tests/hotfix-check.test.js` into about six files by area; (2) tests never reach the npm registry; (3) the test-writing agents get fast-test rules; (4) if time allows, as separate slices: hooks called in the test's own process, and whole-repository scans computed once per file. His process: test first; reviews split by area and run in parallel; only the affected tests while building; the full `npm test` once at completion; the suite's wall-clock and processor time measured before and after each slice and recorded in the plan. `tests/iron-loop-enforcer.test.js` and `tests/reachability-surface-scan-is-linear.test.js` are not touched (another round is changing them).

His words for slice 2, verbatim, from the same brief (2026-10-12):

> "Tests never reach the npm registry. The security-scan tests run `npx eslint` and `npm audit` in temporary projects without eslint, so they download and run whatever the registry serves. That is a security problem as well as slow (30–310 s wall). Use an injected command runner or a local eslint, and keep one deliberately live check only if a real contract needs it, clearly marked."

The paragraph above it is a summary in substance, not a quotation; this block is the only quotation of his slice-2 words in this plan.

### The problem in one paragraph

One test file, run in sequence inside one process, sets the floor under the whole suite. Two test files download and start eslint from the npm registry because the product's own security scan does, which is slow, depends on the network, and runs unpinned code from the registry on the machine (in CTOC's tests and in a user's project). One test accepts either outcome of a live `npm audit`, so it proves less than it reads. And the agents that write the tests carry no rule that keeps new tests fast. The owner wants a faster suite that proves at least as much as today, shown by a recorded comparison rather than asserted.

## 2. ALIGN — Approach

### Business alignment

**Job to be done:** When I or a build agent change CTOC, I want the suite to finish quickly and still prove everything it proves today, so I can get an honest green or red without waiting minutes or trusting a download.

- **Goal:** a faster feedback loop with no loss of proof, and no code from the registry run by a test or by the security scan.
- **Actor:** the owner, and the build agents that run the suite for him.
- **Impact:** the changed test files run faster in paired runs, the suite's longest file is shorter, and the suite's processor time does not grow (measured and recorded as "How every slice is measured" says); no test reaches the registry (counted, zero); new tests written by the agents follow fast-test rules.
- **Deliverable:** five slices in the owner's order; slices 4 and 5 are built if time allows (his words).

### What "never weaker" means, checkably

- **A moved test** keeps its name and its source text word for word, whitespace aside. For slice 1 this is shown by three recorded comparisons between the old file and the new files together with the shared helper module: the multiset of full test names, top-level and subtests, read from the test runner's own output; the multiset of assertion calls, every call whose callee is `assert` or a property of `assert`, read with a JavaScript parser and whitespace-normalised; and every top-level statement of the old file found exactly once in the new files.
- **The exception list.** A moved test that depended on an earlier test's state may have to change to pass on its own. Each such change goes on a named exception list in the build record, carrying the old statement, the new statement, the reason, and a demonstration that the new statement only tightens (it passes in fewer wrong worlds). Criteria 4 and 5 exempt only the statements on that list; any other difference fails them.
- **A changed test** (slices 2, 4 and 5) keeps or tightens what it asserts. "Tighter" means it passes in fewer wrong worlds: an assertion that accepted a finding or a skip becomes one assertion for the finding on a recorded real answer (criterion 18) and one for the skip when the real installed npm faces a closed local registry (criterion 19).
- **A rule test** (slice 3) stays green: every test that reads the edited agent files passes.

After: `SAST skipped for javascript: no scanner installed (need semgrep or eslint)`. `passed` is unchanged; the skipped text changes (criteria 12 and 13).

### How every slice is measured

- **The timing command.** Every before and after measurement runs `node --test` with no coverage: the whole suite as `node --test tests/*.test.js` (`npm run test:raw`, as the baseline did), the changed files as `node --test` with their paths. Each run is timed with `/usr/bin/time` (`-p` gives wall-clock, user and system time). The completion `npm test` is the gate (criterion 2), not a measurement; a build's Step 14 run is not a measurement either.
- **No load threshold.** The machine is shared with other worktrees and its load stayed between 12 and 37 all day, so no run would ever count as quiet. Every run records its load instead.
- **"Faster" is shown by three measures together:**
  - (a) **Paired, interleaved runs of only the changed test files**: before, after, before, after (the before side from the base commit), each with its one-minute load at start and end. Faster is claimed only when every pair agrees.
  - (b) **The longest file within each whole-suite run**, read from the runner's own per-file durations. Every file in one run shares that run's load, so the longest file tracks the suite's floor at the same load for all files.
  - (c) **Whole-suite processor time before and after**, as the check that the work did not grow. If it grew, the record says so with both numbers and the slice is not called faster.
- **Whole-suite wall-clock time** is recorded with its load but is never the only evidence for faster.
- **Before:** the slice's base commit. For slice 1 the CTO Chief's baseline run is the before run (section 1); for later slices it is the previous slice's after-run when nothing else landed in between, otherwise a new run of the timing command.
- **After:** one whole-suite run of the timing command on the completion commit, plus the paired runs of measure (a).
- **Recorded for each run:** the command; wall-clock time; processor time (user plus system time of the whole process tree as `/usr/bin/time` reports it for the finished run); the one-minute load average at start and at end; the core count; the Node version; the commit; passed, failed and skipped counts; the per-file durations from the runner's output and the longest file; and which external scanners are installed on the machine (semgrep, osv-scanner, trufflehog, detect-secrets, gosec, bandit), because the security tests behave differently with them.

### Risks

- **Splitting raises peak load.** Six hotfix files that each start git and Node processes now run at once. The ratio timing tests take the minimum of five runs and compare ratios, so they should hold, but the suite already fails at high load. Mitigation: each new file is run alone three times and all six together (criterion 7); the after-run's load is recorded.
- **A test that depended on an earlier test's state** fails once it moves. That is detection, not damage: it is fixed in the test before the split lands, and the change goes on the named exception list (section 2, under "What 'never weaker' means, checkably") with the old and new statement, the reason and the demonstration that it only tightens.
- **Removing the npx path changes behaviour for a project whose eslint is installed only globally,** if today's npx found it (not checked). Such a project now gets the loud skip. A project managed by Yarn's plug-and-play mode, with no `node_modules` folder, also gets the loud skip.
- **On Windows, eslint security scanning may start working for the first time** (by reading it fails to start today), so a push on Windows with eslint and its security plugin installed can newly be blocked by a real finding. That is the scan doing its job; it is stated so it is not a surprise.
- **A recorded `npm audit` answer can go stale** when npm changes its output. The recording stores the npm version that produced it; a refresh is a one-command re-capture. The live check of criterion 19 runs the installed npm, so a change in how npm reports an unreachable registry shows there.
- **The real npm may answer an unreachable registry in a way the auditor reads as a clean pass.** Criterion 19 then stays red: that is a product defect found, reported to the owner with the captured output; the assertion is never relaxed.
- **Rule text does not make a model obey.** The presence test proves the rules ship, not that agents follow them; only a later look at tests the agents write can show that.
