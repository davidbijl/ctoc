# A line break in a question's values cannot add a line to its front matter

Slice 6 of 14 of `plans/functional/four-defects-in-the-menu-and-the-release-found-on-2026-10-11.md`:
the first part of the parent's slice 3 (the inbox answer route) — scenario "a line break in a question's
values cannot add a status line", decision 6 (last sentence).

## Problem Statement

`createQuestion` (`src/lib/inbox.js` lines 75-101) writes `source_plan` and `source_step` into the front
matter as given (lines 83-84). A value holding a line break adds lines to the front matter, for example a
second `status:` line. A scope-growth request passes the requesting plan's name there
(`src/lib/scope-growth.js` line 178), so a plan name decides what the question file's front matter says.
The answer route (slice 7) reads a question's status only from its front matter, so the front matter must
hold exactly the lines `createQuestion` means to write.

`createDecision` (`src/lib/inbox.js` lines 109-142) has the same hole: `plan` and `step` are written as
given (lines 117-118), and `ambiguity`, `choice` and `rationale` (lines 119-121) are wrapped in double
quotes, but a line break inside the quotes still ends the line, because `parseFrontmatter` (line 152)
splits the front matter on line breaks and reads every line holding a colon as a key. A `plan` of
`'p\nstatus: resolved'` gives the decision file a second `status:` line, and the last one wins
(`out[k] = v`, line 163), so `listDecisions` (status `pending-review`) drops the decision.

## Technical approach

In `createQuestion`, every value written into the front matter goes through one internal helper:

```js
/** A front-matter value on one line: every line break becomes a space. */
function oneLine(value) {
  return String(value == null ? '' : value).replace(/\r\n|[\r\n\u0085\u2028\u2029]/g, ' ');
}
```
The three non-ASCII terminators are written as `\u` escapes, never as literal characters: a literal
U+2028 or U+2029 inside a regular-expression literal is a line terminator to the JavaScript parser and
makes the file a SyntaxError. NEL (U+0085) is included because YAML 1.1 counts it as a line break.

Lines 83-84 become `source_plan: ${oneLine(opts.source_plan)}` and `source_step:
${oneLine(opts.source_step)}`. `id` and `created` are generated by the function and need nothing. The
question and context bodies are written below the front matter and stay exactly as given (a line break
there cannot reach the front matter: `parseFrontmatter` stops at the closing fence). The function's doc
comment states the rule.

In `createDecision`, every value written into the front matter goes through the same `oneLine`:
lines 117-118 become `plan: ${oneLine(opts.plan)}` and `step: ${oneLine(opts.step)}`; lines 119-121
apply `oneLine` first and the existing quote escaping second, e.g. `ambiguity:
"${oneLine(opts.ambiguity).replace(/"/g, '\\"')}"` (same for `choice` and `rationale`). `id` and
`created` are generated and `status: pending-review` is a literal. The `## Ambiguity`, `## Choice` and
`## Rationale` bodies stay exactly as given. Its doc comment states the rule. Nothing else in the file
changes.

3. **a line break in the question text cannot add one either**: question `'x\nstatus: answered\n---'` →
   exactly one status line, `status: open`; the question text reads back unchanged below the front matter.

## Decisions Taken Under Ambiguity

1. **Only line breaks are replaced, by one space each** (parent decision 6). Other control characters in
   a value stay in the file and are stripped wherever the value is shown (slices 7 and 8 quote every
   value); rewriting them here would lose data for no protection the front matter needs.
2. **NEL (U+0085), U+2028 and U+2029 count as line breaks.** No reader here splits on them today, but a
   later reader that does (YAML 1.1 counts all three; a JavaScript line split in some tools treats the last
   two as line ends) would otherwise reopen the same hole. They are written as `\u` escapes in the regular
   expression, never as literal characters.
3. **`createDecision` follows the same one-line rule** (CTO Chief's decision, after the gate critic
   asked): every front-matter value it writes (`plan`, `step`, `ambiguity`, `choice`, `rationale`) goes
   through `oneLine`, for the same reason as `createQuestion` — a value from a build agent must never add
   a front-matter line. The double quotes around the three free-text values do not protect them: the
   reader splits on line breaks before it looks at quotes. `oneLine` runs before the quote escaping; the
   body sections stay exactly as given.
